Without cache

~120 ms

per read · DB CPU burns on the same query, 10,000 times. DB becomes the bottleneck and a single point of collapse under load.

With Redis in front

~1–2 ms

per read · data served from RAM, no disk, no query planning. DB only sees the first request; the rest are absorbed by the cache.

💡 Key insight: most workloads are read-heavy (80–95% reads). If the answer rarely changes, why compute it every time?

Redis = a Giant, Blazing-Fast Dictionary in RAM

  • In-memory key–value store — data lives in RAM, not disk → microsecond access
  • Single-threaded event loop for commands → operations are atomic, no locks needed
  • Rich types: strings, hashes, lists, sets, sorted sets
  • Typical roles: cache, session store, rate limiter, leaderboard, pub/sub

⚠️ RAM is fast but small and expensive — we can't keep everything forever. That's exactly why TTL and eviction policies exist (coming up!).

// think of it as a network-attached Map (Node.js) import { createClient } from 'redis'; const redis = createClient(); await redis.connect(); await redis.set('product:42', JSON.stringify(product)); await redis.get('product:42'); // → JSON, in ~1ms // store WITH an expiry (TTL) of 60 seconds await redis.set('product:42', json, { EX: 60 }); await redis.ttl('product:42'); // → 57 (secs left) await redis.get('product:42'); // after 60s → null

The hierarchy of speed: CPU cache < RAM (Redis) < SSD < network DB query.

TTL — Time-To-Live live demo

  • Every key can carry an expiry timer: SET key val EX 10
  • When the timer hits 0, Redis deletes the key — a later GET returns (nil)
  • Why? Guarantees stale data has a bounded lifetime → cache stays “fresh enough”
  • Choosing TTL is a trade-off:
    short TTL → fresher data, more DB load · long TTL → fewer DB hits, staler data
// pick TTL per use-case (JavaScript, node-redis) await redis.set('otp:9911', '4821', { EX: 8 }); await redis.set('session:amy', tok, { EX: 20 }); await redis.set('config:site', cfg, { EX: 45 }); await redis.ttl('session:amy'); // → secs left

LRU — What Happens When Memory Runs Out?

TTL removes keys on a schedule. But what if memory fills up before anything expires?

  • Redis has a memory ceiling: maxmemory 2gb
  • When full, an eviction policy decides who gets kicked out
  • LRU = evict the key that was used longest ago
  • Intuition: “if nobody asked for it recently, nobody will soon” — temporal locality
  • Bookshelf 📚: every book you read goes back on the left end; when the shelf is full, the right-most book (untouched longest) falls off
# redis.conf — turn Redis into an LRU cache maxmemory 2gb maxmemory-policy allkeys-lru

(Real Redis uses an approximated LRU — it samples keys instead of tracking a perfect list, to save memory.)

The classic interview question — in JavaScript

// O(1) LRU — a JS Map remembers insertion order! class LRUCache { constructor(cap) { this.cap = cap; this.m = new Map(); } get(k) { if (!this.m.has(k)) return null; // MISS const v = this.m.get(k); this.m.delete(k); this.m.set(k, v); // bump to MRU end return v; // HIT } put(k, v) { this.m.delete(k); // refresh position if (this.m.size >= this.cap) // full → evict LRU: this.m.delete(this.m.keys().next().value); this.m.set(k, v); } }

Redis Caching — Putting It Together

The full read path

// cache-aside in JavaScript async function getUser(id) { const key = `user:${id}`; const cached = await redis.get(key); if (cached) // HIT → ~1ms return JSON.parse(cached); const user = await db.query(id); // MISS → ~120ms await redis.set(key, JSON.stringify(user), { EX: 300 }); return user; }
  • TTL bounds staleness — data self-destructs on schedule
  • LRU bounds memory — coldest data leaves first when RAM is full
  • They work together: TTL = freshness policy, LRU = capacity policy
  • On writes: await redis.del('user:42') (invalidate) so the next read repopulates

⚠️ Watch-outs

Stale reads within TTL · cache stampede (many misses at once — fix with locks/jitter) · never treat cache as the source of truth.

Part 2 — The Producer–Consumer Problem

An order placed on a shopping site triggers: payment, inventory, email, shipping, analytics… Should the checkout API wait for all of that? 😰

🛒 Checkout APIproducer — fast, returns 200 immediately
➜
📨 Kafka Topic: ordersdurable, ordered, replayable log
➜
⚙️ Order Processorsconsumers — work at their own pace

Why a queue in between?

  • Decoupling — producer doesn't know/care who consumes
  • Buffering — flash sale spike? The log absorbs it, consumers drain it steadily
  • Resilience — consumer crashes? Messages wait; nothing is lost

Why Kafka specifically?

  • Messages are persisted to disk & replicated — it's a log, not just a queue
  • Consumers track their own offset → replay/rewind possible
  • Horizontal scale via partitions (next slide)

Kafka Anatomy: Topics, Partitions, Offsets, Groups

  • Topic — a named stream (e.g. orders); split into partitions
  • Partition — an append-only log; each message gets a sequential offset (0,1,2,…)
  • Key → partition: hash(customerId) % 3 — same customer always lands in the same partition → ordering per customer is guaranteed
  • Consumer group — consumers share the work; each partition is owned by exactly one consumer in the group

⚖️ Consequence: max useful consumers in a group = number of partitions. Lag = produced offset − consumed offset = your backlog.

// topic "orders" = 3 append-only logs (offsets 0,1,2…) // P0 │o12│o15│o18│ ◀ append P1 │o13│o16│ P2 │o14│o17│o20│ // PRODUCER (checkout API) — JavaScript, kafkajs await producer.send({ topic: 'orders', // key decides the partition ↓ messages: [{ key: customerId, value: JSON.stringify(order) }], }); // CONSUMER GROUP — brokers split partitions across members const consumer = kafka.consumer({ groupId: 'order-processors' }); await consumer.subscribe({ topic: 'orders' }); await consumer.run({ eachMessage: async ({ partition, message }) => { await processOrder(JSON.parse(message.value)); }, // offset auto-commits after success });

Recap — Two Tools, Two Superpowers

Redis Cache
  • RAM-speed reads shield your DB (cache-aside: check → miss → fill)
  • TTL = freshness knob — keys self-expire
  • LRU = capacity knob — coldest keys evicted when memory is full
  • Solves: latency & read scalability
Kafka Queue
  • Producers & consumers decoupled by a durable, partitioned log
  • Key → partition preserves per-customer ordering
  • Scale by adding consumers (up to #partitions) — group rebalances
  • Solves: spikes, decoupling, reliability
